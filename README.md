### Clones

Every NixOS host removes a clone under `/tmp/git` as a whole, so an agent finds every file of a clone or no clone at all. The OrbStack machine and the [sandbox VM](#sandbox-vm) are NixOS hosts too. Agents clone other repositories into `/tmp/git/<owner>/<repo>` and read them there. `hosts/nixos/default.nix` imports `hosts/nixos/clones.nix`, which holds the settings that keep the clones whole:

- A `systemd-tmpfiles` rule keeps the daily cleanup of `/tmp` out of `/tmp/git`. That cleanup checks each file on its own and deletes a file that nothing read or changed in the last 10 days. Without the rule, a clone loses each file that no agent read and no fetch wrote in that time. The sandbox VM mounts the root filesystem with `noatime`, so a read leaves no trace on a file there. Without the rule, a clone in the VM keeps only the files of its last fetch.
- `expire-clones.service` runs every day and removes each clone that nothing changed in the last 10 days. `cloneMaxAge` sets that span. Every fetch changes its clone, so each `mcp__git__git_clone` call that pulls a clone keeps it for 10 more days. Reads do not change a clone. The service leaves a clone alone while a clone, fetch, pull, or push call of the git MCP server works on it.

The settings apply only on a host that keeps the `git` bundle of `dotfiles.claude.toolBundles` on, and the bundle is on by default. On a Linux host, that bundle tells agents to clone into `/tmp/git`.

The service runs as root, as the cleanup of `/tmp` does. So it reads a directory whose mode keeps the user out. It also removes the files that it cannot remove as the user, such as a file in a directory with the mode 755 that a rootless container made with a subordinate uid. It removes a symbolic link in `/tmp/git` and keeps the files of the target, and systemd lets it write only in `/tmp/git`.

The service keeps each clone that holds a mount, so it does not delete the files of the source of a bind mount. It also keeps each owner directory that is a mount point. The cleanup of `/tmp` skips such a mount too. Until someone removes the mount, each run fails and names the directory that holds it.

`pkgs/expire-clones.nix` describes what counts as a clone and as a change. The build of each configuration runs the cleanup of `/tmp` on a sample clone, and it fails when the cleanup deletes a file of that clone. The evaluation of a NixOS host fails when the bundle is on and the host lacks the rule. To list the clones that the service removed, run this command on the host:

```sh
journalctl -u expire-clones.service -g removed
```

When a run cannot remove an old clone, it keeps the clone, names it, and fails. It does the same for an empty owner directory that it cannot remove. To list those clones and directories, run this command on the host:

```sh
journalctl -u expire-clones.service -g stay
```

To apply the settings, run `task switch` on the host. For the OrbStack machine, run `task vm:switch` on the Mac. A clone that lost files to the cleanup of `/tmp` before the switch stays incomplete, and the service removes it 10 days after its last change. To remove every clone now, wait until no session reads a clone. Then run this command on the host:

```sh
rm -rf /tmp/git
```

### Session files

Every NixOS host removes a session directory of Claude Code as a whole. So a session finds every file of its scratchpad or no file at all. Claude Code keeps the temporary files of each session in `/tmp/claude-<uid>/<project>/<session>`. Those files are the scratchpad of the session and the output of its background commands. `hosts/nixos/default.nix` imports `hosts/nixos/claude-tmp.nix`, which holds the settings that keep the files whole:

- A `systemd-tmpfiles` rule keeps the daily cleanup of `/tmp` out of `/tmp/claude-<uid>`. That cleanup checks each file on its own and deletes a file that nothing read or changed in the last 10 days. Without the rule, a session that lives for more than 10 days loses each file of its scratchpad that it did not read or write in that time. The sandbox VM mounts the root filesystem with `noatime`, so a session there also loses the files that it reads every day.
- `expire-claude-tmp.service` runs every day and removes each session directory that nothing changed in the last 10 days. `maxAge` sets that span.

The service keeps these session directories, however old their files are:

- The directory named by the current id of each session that runs. Claude Code keeps one file in `~/.claude/sessions` for each session that runs, and the service reads those files. When the service cannot read that directory or one of its files, it removes no session directory and fails.
- Each directory that a process uses. A process uses a directory when it holds the directory or a file under it open, or when its working directory lies there. The service reads the open files and the working directories from `/proc`. Each background command holds its output file open, so the directory of that file stays while the command runs.
- Each directory that holds the socket of a server that listens, such as a `tmux` server that a command started. The cleanup of `/tmp` keeps such a socket too. The service finds those servers in `/proc/net/unix`, which lists only the sockets of its own network namespace.

Claude Code keeps the output of the background commands of a session under the id that its process started with. On Linux, Claude Code 2.1.319 holds that directory open while its process runs. So the directory stays after `/clear` gives the session another id.

The service removes the directory of a session that does not run 10 days after the last change to the directory. A session that you resume after that time finds none of its earlier scratchpad files.

The service runs as root, as the cleanup of `/tmp` does. So it removes the files that it cannot remove as the user, such as a file in a directory with the mode 755 that a rootless container made with a subordinate uid. It never follows a symbolic link out of `/tmp/claude-<uid>`, and systemd lets it write only in `/tmp`.

The service keeps each session directory that holds a mount, so it does not delete the files of the source of a bind mount. It also keeps each project directory that is a mount point. The cleanup of `/tmp` skips such a mount too. Until someone removes the mount, each run fails and names the directory that holds it.

The `claude` wrapper of `home/claude.nix` sets `CLAUDE_CODE_TMPDIR` to `/tmp`. Without the variable, Claude Code on Linux follows `TMPDIR`, so a session that starts in a shell with another `TMPDIR` keeps its files outside `/tmp/claude-<uid>`.

`pkgs/expire-claude-tmp.nix` describes what counts as a session directory and as a change. The build of each configuration runs the cleanup of `/tmp` on a sample session directory. The build fails when the cleanup deletes a file of that directory. The evaluation of a NixOS host fails when the host lacks the rule. To list the session directories that the service removed, run this command on the host:

```sh
journalctl -u expire-claude-tmp.service -g removed
```

When a run cannot remove a session directory, it keeps the directory, names it by its path, and fails. It does the same for an empty project directory that it cannot remove. To list those directories, run this command on the host:

```sh
journalctl -u expire-claude-tmp.service -g stay
```

To apply the settings, run `task switch` on the host. For the OrbStack machine, run `task vm:switch` on the Mac. A session directory that lost files to the cleanup of `/tmp` before the switch stays incomplete. After the switch, the first run of the service keeps the directory named by the current id of each session that runs. It removes each other session directory whose last change is more than 10 days old.

### Clones

Each Darwin host keeps the clones of agents outside `/tmp`, so an agent finds every file of a clone or no clone at all. Agents clone other repositories into `~/Library/Caches/git-clones/<owner>/<repo>` and read them there. `cloneRoot` in `home/claude.nix` sets that directory.

macOS 14 and later clean `/tmp` every day with `/usr/libexec/tmp_cleaner`. The script checks each file on its own and deletes a file that nothing read or changed in the last three days. A clone in `/tmp` then loses each file that no agent read and no fetch wrote in that time. The script reads no setting, so a Darwin host cannot keep the script out of a directory. The evaluation of a Darwin host fails when the `git` bundle of `dotfiles.claude.toolBundles` is on and `cloneRoot` lies in `/tmp`.

The script does not clean `~/Library/Caches`, so a launchd agent bounds the clone directory. The `expire-clones` agent runs every day at 04:00 and at each login, and it removes each clone that nothing changed in the last 10 days. It runs the tool that `expire-clones.service` runs on the NixOS hosts, so `pkgs/expire-clones.nix` describes what counts as a clone and as a change. The agent runs only on a host that keeps the `git` bundle on. To list the clones that the agent removed, run this command on the Mac:

```sh
grep removed ~/Library/Logs/expire-clones.log
```

The agent runs as the user, so it cannot remove every clone. It keeps a clone that holds a directory that the user cannot read. When a clone holds a file that the user cannot delete, the agent renames the clone to `.expired.<random>` and keeps the renamed directory. In both cases the run fails and names the clone. It does the same for an empty owner directory that it cannot remove, such as when the user cannot write the clone directory. To list those clones and directories, run this command on the Mac:

```sh
grep stay ~/Library/Logs/expire-clones.log
```

Delete each of those clones and directories by hand. Use `sudo` when a file of the clone belongs to another user.

To apply the settings, run `sudo task switch` on the Mac. Then restart each Claude Code session that started before the switch, because such a session still clones into `/tmp/git`. The switch leaves the clones in `/tmp/git` where they are. macOS deletes their files, and it empties `/tmp` at each restart. To remove them now, run this command on the Mac:

```sh
rm -rf /tmp/git
```

### Session files

Each Darwin host keeps the temporary files of Claude Code outside `/tmp`. So a session finds every file of its scratchpad or no file at all. Claude Code keeps the files of each session in `~/Library/Caches/claude-tmp/claude-<uid>/<project>/<session>`. Those files are the scratchpad of the session and the output of its background commands. `claudeTmpDir` in `home/claude.nix` names `~/Library/Caches/claude-tmp`, and the `claude` wrapper passes that directory to Claude Code as `CLAUDE_CODE_TMPDIR`.

The `tmp_cleaner` script of macOS deletes each file under `/tmp` that nothing read or changed in the last three days. No setting keeps the script out of a directory. In `/tmp`, a session that lives for more than three days loses single files of its scratchpad and keeps the others. The evaluation of a Darwin host fails when `claudeTmpDir` lies in `/tmp`.

The script does not clean `~/Library/Caches`, so a launchd agent bounds the directory. The `expire-claude-tmp` agent runs every day at 04:30 and at each login. It removes each session directory that nothing changed in the last 10 days. It runs the tool that `expire-claude-tmp.service` runs on the NixOS hosts, so `pkgs/expire-claude-tmp.nix` describes what counts as a session directory and as a change. To list the session directories that the agent removed, run this command on the Mac:

```sh
grep removed ~/Library/Logs/expire-claude-tmp.log
```

The agent keeps these session directories, however old their files are:

- The directory named by the current id of each session that runs.
- Each directory that a process of the user uses. A process uses a directory when it holds the directory or a file under it open, or when its working directory lies there. The agent asks `lsof` for the open files. Each background command holds its output file open, so the directory of that file stays while the command runs.
- Each directory that holds a socket. macOS does not list the sockets that servers bind, so the agent cannot tell whether a server listens on a socket.
- Each directory that the agent cannot read in full, such as a directory with the mode `000`. The agent runs as the user, so the run fails, and the log names the directory.

The agent runs as the user, so it cannot remove every old session directory. It keeps each session directory of a project directory that the user cannot write. When a session directory holds a file that the user cannot delete, the agent renames the session directory to `.expired.<random>` and keeps the renamed directory. In each case the run fails and names the session directory by its path. It does the same for an empty project directory that it cannot remove, such as when the user cannot write `~/Library/Caches/claude-tmp/claude-<uid>`. To list the directories that the runs kept and named, run this command on the Mac:

```sh
grep stay ~/Library/Logs/expire-claude-tmp.log
```

Claude Code keeps the output of the background commands of a session under the id that its process started with. On macOS, Claude Code 2.1.319 holds that directory open only while it writes there. After `/clear` gives a session another id, the agent removes that directory 10 days after its last change, even while the session runs. A background command that still runs keeps the directory.

Sandboxed commands still get `/tmp/claude-<uid>` as `TMPDIR`. The path of `~/Library/Caches/claude-tmp/claude-<uid>` is too long for a Unix socket, so Claude Code does not pass that directory to the commands. macOS therefore still deletes single files that a command keeps in `TMPDIR` for more than three days. Files that a session needs for longer belong in its scratchpad.

Claude Code creates `/tmp/claude-<uid>` once for each process, so each sandboxed command of a session fails after the directory is gone. The directory often stays empty, and the `tmp_cleaner` script deletes an empty directory that nothing modified in three days. So each run of the agent creates the directory when it does not exist, and it sets the modification time of the directory.

To apply the settings, run `sudo task switch` on the Mac. Then quit each Claude Code session that started before the switch, because such a session still keeps its files in `/tmp/claude-<uid>`. The switch leaves those files there, so a session that you resume later finds none of its earlier scratchpad files. To keep the files, run these commands on the Mac before you start a session again:

```sh
mkdir -p ~/Library/Caches/claude-tmp
mv -n "/private/tmp/claude-$(id -u)" ~/Library/Caches/claude-tmp/
```

### Kubernetes contexts

Each Darwin host keeps the kubectx files of a session outside `/tmp`. So a session keeps the Kubernetes context that it selected for as long as it runs. The `claude` wrapper creates the directory `~/.local/state/claude-kubectx/claude-kubectx.<pid>` for each session. That directory holds `local.yaml`, which records the context that the session selected, and the `kubeconfig` link to the scoped kubeconfig of that context. `kubectxSessionParent` in `home/claude.nix` names `~/.local/state/claude-kubectx`.

The `tmp_cleaner` script of macOS deletes each file under `/tmp` that nothing read or changed in the last three days. In `/tmp`, a session loses `local.yaml` when nothing reads or changes the file for more than three days. The `hook-router` tool then denies each `kubectl` command of the session until the agent selects a context again. The evaluation of a Darwin host fails when `kubectxSessionParent` names no directory, or a directory in `/tmp`.

The script does not clean `~/.local/state`, and a restart of the Mac does not empty it. So `hook-router` and the `claude` wrapper remove the directories in `~/.local/state/claude-kubectx`:

- `hook-router` removes the directory of a session when the session ends.
- At each session start, `hook-router` removes each directory whose process has exited.
- The wrapper removes the directory of its own PID before it creates that directory. Sessions that end without the SessionEnd hook, such as after a crash or a restart, leave their directories behind. When a later session gets the PID of such a directory, it still starts with no selected context.

The kubectx files do not lie in `~/Library/Caches`, where sandboxed commands can write. Sandboxed commands can read `~/.local/state`, and no write path of the sandbox holds `~/.local/state/claude-kubectx`. So they read the files of a session and cannot change them.

To apply the setting, run `sudo task switch` on the Mac. Then restart each Claude Code session that started before the switch, because such a session still keeps its files in `/tmp/claude-kubectx.<pid>`.

## Sandbox VM

Workmux runs sandboxed agents in a Lima VM that boots the NixOS configuration in `hosts/nixos/terrarium.nix`. `limactl list` shows the VM as `wm-<hash>`. The `dotfiles.claude.lima` option in the host's file under `hosts/darwin/` sets the CPUs, the memory, and the disk of the VM.

### Resize

Workmux reads `dotfiles.claude.lima` only when it creates the VM. To resize a VM that exists, you must also edit its Lima config. Lima can grow a disk but cannot shrink it.

1. Set the new values in `dotfiles.claude.lima`. A VM that workmux creates later gets them.
2. In the VM, run `task switch` so that the VM runs the current configuration. That configuration includes `growpart.service`, which grows the root partition at boot.
3. Wait until no session in the VM has work in progress. Stopping the VM ends every session, build, and container in it.
4. On the Mac, find the name of the VM and stop the VM:

   ```sh
   limactl list
   limactl stop <name>
   ```

5. Set the new disk size and start the VM:

   ```sh
   limactl edit <name> --set '.disk = "1TiB"' --start
   ```

6. In the VM, check that the root partition `vda2` and the filesystem grew:

   ```sh
   lsblk /dev/vda
   df -h /
   ```

Lima grows the disk image when the VM starts. In the VM, `growpart.service` then grows the root partition, and `systemd-growfs-root.service` grows the filesystem. If `vda2` kept its old size, the VM runs a configuration that lacks `growpart.service`. Run `task switch` in the VM, then stop and start the VM again. If `vda2` grew but `df -h /` still shows the old size, run `sudo resize2fs /dev/vda2` in the VM.

To change the CPUs or the memory, set `.cpus` or `.memory` with the same `limactl edit` command.

### Memory

The VM has no swap, so the kernel kills a process when memory runs out. These settings in `hosts/nixos/terrarium.nix` decide which process the kernel kills and bring the user manager back after a kill:

- `sessionMemoryMax` limits the processes of one login to a share of the VM's memory. Workmux starts every agent with `limactl shell`, and Lima carries those shells over one SSH connection, so every agent runs in one login. When the processes of that login need more than the limit, the kernel kills the largest of them and no process outside the login.
- `OOMScoreAdjust` on `user@.service` puts the user services, such as rootless Docker, level with the commands of a login. When the whole VM runs out of memory, the kernel kills the largest process first.
- `Restart` on `user@.service` starts the user manager again after a signal kills it.

To list the processes that the kernel killed today to free memory, run this command in the VM:

```sh
journalctl -k --since today -g 'Killed process'
```

`task switch` applies a new `sessionMemoryMax` and a new `Restart` to the running VM. The user manager and its services get a new `OOMScoreAdjust` only when the manager starts. To apply it, reboot the VM or restart the manager. The restart stops every user service and every rootless Docker container, so wait until no session uses Docker. Then run this command in the VM:

```sh
sudo systemctl restart "user@$(id -u).service"
```

### Session variables

Each agent in the VM gets the `home.sessionVariables` entries and the `home.sessionPath` directories of the home-manager configuration. Workmux starts each agent from a bash login shell, and home-manager manages only fish on this host. So `hosts/nixos/terrarium.nix` makes `/etc/profile` source the home-manager script that exports these entries. The evaluation of the host fails when `/etc/profile` does not source the script, or when the script does not export an entry.

A bash login shell and fish get the same `PATH`. The `home.sessionPath` directories come first, then `/run/wrappers/bin`, then the Nix profiles, and `/run/current-system/sw/bin` comes last. Workmux and devbox then put their own directories ahead of these in the `PATH` of an agent.

Run `task switch` in the VM after you change these entries. The switch applies the change to each agent that workmux starts after it. Agents keep the environment that they started with, so restart each agent that started before the switch. To check a session, run this command in it, which prints `1` when the session has the home-manager variables:

```sh
printenv __HM_SESS_VARS_SOURCED
```

### Dagger engines

Each Dagger version keeps its own engine container in the VM. Sessions in repositories that pin different Dagger versions can therefore run Dagger at the same time. `docker ps` lists each engine as `dagger-engine-<version>`.

The `DAGGER_LEAVE_OLD_ENGINE` variable keeps the engines. Without it, a Dagger CLI removes the engine containers of every other version each time it connects to its own engine. A call on a removed engine then hangs without output. `home/tools.nix` sets the variable in `home.sessionVariables`, and the [Session variables](#session-variables) section describes how the agents get it.

Run `task switch` in the VM. The switch applies the variable to each agent that workmux starts after it. Agents keep the environment that they started with, so restart each agent that started before the switch. To check a session, run this command in it, which prints `1` when the session has the variable:

```sh
printenv DAGGER_LEAVE_OLD_ENGINE
```

An engine stays in the VM after every project moves to another Dagger version, and it keeps its cache. To free the disk space, list the engines and remove the engine of each unused version. Before you remove an engine, wait until no session runs a Dagger call on it. A call on the engine that you remove hangs without output. These commands list the engines and remove one of them:

```sh
docker ps -a --filter name=dagger-engine-
docker rm -fv dagger-engine-<version>
```
